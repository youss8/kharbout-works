# First-principles database & invariant architect

You are designing the persistence boundary for Equipment custody and time-bound loans on PostgreSQL. Work within 150 members, 1,000 assets, simultaneous checkouts at three branches. Distinguish requirements supplied by the owner from assumptions that need confirmation.

1. Name the entities, their lifetimes, natural identifiers and tenant boundary. For each relationship, state its cardinality and what should happen when a participant is retired.
2. Write invariants as testable sentences. For each, choose a unique constraint, check, foreign key, isolation rule or ordered lock sequence supported by the selected engine. Explain the remaining failure window.
3. Trace two simultaneous writes against the same resource. Show what each transaction reads, which rows it locks, the winning commit and how the losing caller recovers without duplicating work.
4. Derive indexes from named reads. Give key order and filters, consider a partial index where the engine supports one, and state its expected write cost.
5. Cover creation, retry, cancellation, rollback and historical reads. Use a fictional two-record example with expected final rows.

Return an entity table, an invariant-to-enforcement table, an ordered transaction outline and three acceptance checks. List outstanding decisions before proposing a migration.

Turn this functional report into a fix specification for Astro, Alpine.js and static fixtures.

User journey: Filter a catalogue, clear filters, return to the full list
Reported observation: After I clear the status filter, the list stays empty until I reload.

Separate what the reporter actually observed from hypotheses. Give the smallest reproducible fixture, starting state and ordered actions. State an observable expected and actual outcome after each significant change. If a detail is missing, label it unknown and propose one focused clarification.

# Expand–contract migration playbook

Plan a migration of equipment_loans from member_id to custodian_id while old and new application versions coexist.

List current readers, writers, queued jobs and exports. Specify the meaning of null, any conversion rule and the stable key used to resume a backfill. Stop and ask for those details if lossless conversion cannot be established.

Sequence the rollout into independently deployable changes. Add the compatible column, introduce coordinated writes, run bounded idempotent batches, verify parity, switch reads, retire old writers and finally remove the old column after the agreed window. For each stage, identify the safe previous app version, expected locks, monitoring query and rollback action.

Return a deployment table with preconditions, measurable exit criteria and an owner for each irreversible decision. Include a verification sample covering a null value, a concurrent update during backfill and a retried batch. Never claim zero downtime without the engine-specific lock and deployment assumptions.
