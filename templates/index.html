Architecture / md

System Architecture Spec

Decide the data boundaries, lifecycle, permissions and rollout for a new operational workflow.

○ Starter blueprint

Pre-code architecture record

Record the decision owner, review date, affected teams and links to evidence. This worked example scopes a fictional equipment checkout at one branch. Replace its entities and acceptance criteria with the ones your team can verify.

Problem and acceptance

Two operators can reserve the same asset while working with separate spreadsheets. A custodian needs one answer to “who has this device now?” The first release covers checkout, return and the custody history. Procurement belongs to a separate workflow.

Accept the design when two simultaneous requests for one device yield one active loan, and a return makes the device available without removing its previous custody record.

Domain boundaries

Entity Identity and relationships Owner of changes
Asset Stable asset ID, one home branch Register service
Member Stable member ID, one current branch Directory service
Loan Asset, borrower, issuer, issued time, optional returned time Custody service
Custody event Actor, loan, action and timestamp Append-only audit writer

Lifecycle and invariants

  1. Available → Issued. Lock the asset row, confirm the operator’s branch scope, reject an existing active loan, then write the loan and issue event in one transaction.
  2. Issued → Returned. Lock rows in the same order. Record the return only when the loan remains active. A repeated return reports the established result.
  3. Historical corrections. Append a correction event with its reason and reference to the original event. The original record remains available to the reviewer.

Enforce uniqueness of active custody at the database boundary. In PostgreSQL a partial unique index can cover the asset ID where the return time is null. Document an equivalent guard if the production engine differs.

Access matrix

Actor Read Write Boundary
Borrower Own current and past loans None Member ID
Branch operator Branch assets and custody Issue and return Asset’s home branch
Auditor Authorized custody history None Assigned review scope

Test the same scope on API, background job and user-interface paths. Record how the service obtains the actor identity.

Rollout and recovery

  • Introduce additive tables and indexes. Dry-run the import against synthetic duplicates and retain a rejected-row report.
  • Pilot a single branch. Reconcile active records against the old register before enabling checkout.
  • Watch duplicate rejection counts and unreturned loans. If reconciliation fails, pause new checkouts, preserve the audit history and reconcile against the last accepted export.
  • Record the release owner, fallback owner and the evidence each signs before expanding the rollout.

Planning / md

Pre-Code Readiness Checklist

Confirm ownership and evidence for integrity, concurrent writes, accessibility and recovery before implementation.

○ Starter blueprint

Readiness review

Use one review per proposed workflow. For each line, record the reviewer, evidence, and either an acceptance decision or a dated exception with an owner. A blank decision leaves the item open.

Protect the data

  • List the entities, stable identifiers, null rules, foreign keys and uniqueness constraints. Provide one invalid example that the database must reject.
  • Define valid transitions and transaction boundaries. Record a consistent lock order for two concurrent saves and the expected result of replaying the same request.
  • Specify the source of every calculated total, its rounding policy and the meaning of missing inputs. Keep amounts in separate currency totals.
  • Scope reads and writes by actor and record. Confirm that the caller cannot supply the authoritative actor identity.

Make the workflow usable

  • Describe the initial, empty, loading, stale, failed and completed views. For each recoverable failure, state the retry action and which form values survive.
  • Record the keyboard sequence to open, complete and dismiss the main task. Identify the initial focus target and where focus returns.
  • Inspect a 375px viewport and RTL layout with a long label. Verify table scrolling stays inside its labelled region.
  • Give each status an icon, text and differentiated shape. Confirm all essential information remains readable in grayscale.

Operate and verify it

  • Identify audit events, actor and timestamp sources, redacted fields, retention owner and safe diagnostic context.
  • Define timeouts, bounded retries and idempotency for each external call. State how a human reconciles an ambiguous result.
  • Link runnable examples for one normal transaction, one refused transition, one simultaneous write and one restricted user.
  • Identify the rollout switch, a recovery owner, the last known good state and a rollback rehearsal.

Decision log

Gate Evidence to record Review decision
Concurrent submit Request pair, committed row count, audit IDs Accept after one mutation
Accessibility Keyboard route, mobile capture, RTL reading order Accept after reviewer walkthrough
Recovery Retry result and reconciled external record Accept after supervised rehearsal

Before coding begins, the decision owner records the date, remaining exceptions and the first milestone at which each exception will be revisited.

Operations / md + json

State Machine & Permission Matrix

Define allowed state transitions, the actors who may request them and the evidence each transition requires.

○ Starter blueprint

Workflow transition contract

Record one row per allowed edge. An absent edge is denied. A transition requires both permission on the record and evidence that the named guard passes.

Example review register

From Action To Allowed role and scope Required evidence Audit event
Draft Submit Review Author of this record Required fields complete Submitted
Review Return Draft Reviewer for this branch Written return reason Returned
Review Approve Approved Reviewer for this branch Reviewer differs from author Approved

Machine-readable instance

{
  "version": 1,
  "initial": "draft",
  "states": ["draft", "review", "approved"],
  "roles": ["author", "reviewer"],
  "transitions": [
    {"from":"draft","to":"review","action":"submit","roles":["author"],"requires":["owns_record","complete"],"auditEvent":"submitted"},
    {"from":"review","to":"draft","action":"return","roles":["reviewer"],"requires":["same_branch","return_reason"],"auditEvent":"returned"},
    {"from":"review","to":"approved","action":"approve","roles":["reviewer"],"requires":["same_branch","different_author"],"auditEvent":"approved"}
  ]
}

Enforcement sequence

  1. Validate the document against the downloadable JSON Schema. Check that the initial state, edge endpoints and role references exist in the declared lists. Reject duplicate action names for the same source state.
  2. Resolve the actor from the authenticated session. Scope the record and lock it before re-reading its current version and state.
  3. Locate the declared edge. Evaluate each named requirement against server-owned facts and return a specific rejection if one fails.
  4. Write the new state, increment the version and append the audit event in one transaction. Use an idempotency key for retryable requests.

Verification cases

  • An author submits a complete record once. A replay produces no second transition or event.
  • A reviewer trying to approve their own record is refused. Both the stored state and version remain unchanged.
  • A return without a reason is refused. Supplying a reason updates the review state and records the objection.
  • Two reviewers race on the same version. One transition commits, and the second reviewer sees the updated state.

Planning / md

Scope & Priority Trade-Off Matrix

Compare the delivery, capacity and verification impact of late scope changes before agreeing a release decision.

○ Starter blueprint

Change decision

Capture the current release goal, requested change, target date, decision owner and evidence of user impact. This worked example introduces a new export into a release whose acceptance tests already cover the review queue.

Establish the constraint

The review queue is due at the end of the iteration. An additional export would need field mapping, authorization review, locale checks and a download test. Ask the team to estimate these tasks before making a delivery promise.

Compare feasible choices

Choice What ships now Consequence Evidence before commitment
Keep the release Existing queue with its agreed checks Export moves to the next review Named requester confirms priority
Exchange scope Queue and export, with a lower-priority saved view deferred Existing saved-view users wait longer Owner accepts the deferred view and updated tests
Move the date Queue, saved view and export Release date moves by the reviewed estimate Operations confirms the new window
Deliver a narrower export A documented subset of authorized columns Some reports still need manual preparation Requester validates a sample file

Resolve the decision

  1. Record the user task gained and the work displaced by each option.
  2. Identify immovable constraints such as contractual dates, column-level permissions and access review.
  3. Ask the implementer and reviewer for separate effort estimates. Record any dependency outside their control.
  4. Choose one option. Name the owner, decision time, revised acceptance checks and follow-up date.

Confirmation message

“We agreed to keep the queue release on its current date. The export will enter the next review with an approved field list and a sample file. The product owner will confirm the column set before estimation. The release reviewer will continue to verify access scope and queue transitions.”

Technical Handover Guide

Transfer repository ownership, runtime configuration, scheduled work, operational invariants and acceptance evidence.

○ Starter blueprint

Operational handover

Record the service, release tag, outgoing and receiving roles, handover window and escalation channel. Use references to the access-controlled configuration store for environment settings.

Repository and runtime map

Area What the incoming owner needs Example verification
Entry points Routes, UI shell and job entry modules Trace a sample request to its transaction
Domain layer Allowed transitions, services, policies and data types Locate the guard for an invalid transition
Persistence Migration order, required engine features and indexes Rebuild a disposable database and inspect constraints
Automation CI checks, pinned runtime and release workflow Run the verification suite at the release tag
Configuration Example environment file, names of required settings, rotation owner and storage location Boot with an approved test configuration

Queue and scheduler topology

For each recurring job record its schedule and timezone, overlap rule, queue name, timeout, retry policy and dead-letter destination. Record how to detect a missed run and the safe replay procedure. Confirm that retrying a message cannot issue a second external charge or duplicate an audit event.

Example job Trigger Replay boundary First diagnostic
Daily register reconciliation Daily, 02:00 UTC One result per branch and date Compare last successful date with expected date
Deliver approved notification After committed approval Unique delivery ID per recipient Check outbox state and delivery receipt

Database guarantees and recovery

List the authoritative tables and the transaction that changes each invariant. Record lock order, immutable events, uniqueness and scope restrictions. Walk through one restoration on synthetic data, then compare a known record, aggregate count and latest audit event against the recovery point.

Deliverables and sign-off

Deliverable Status to record Acceptance evidence Receiving role
Release build Verified or outstanding Build and test run at the named revision Engineer
Runtime access Confirmed or outstanding Successful least-privilege access check Operator
Scheduler and recovery Rehearsed or outstanding Timestamped replay and restore record Operator
Known issues Accepted or unresolved Owner, impact and next review date Product owner

The incoming owner runs the setup, traces one write and rehearses one recovery while the outgoing owner observes. Record the acceptance decision and any remaining responsibility by name in the private handover record.
